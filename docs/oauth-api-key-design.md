# CommandCode 双入口认证设计

> 状态：已完成实现、隔离验收与审查，并于 2026-10-19 经另行授权更新到 Kubernetes 中的 CPA；目标公共版本为 [v0.1.2](https://github.com/mczhoucn/commandcode-go-cliproxyapi/releases/tag/v0.1.2)，安装包以该版本发布成功后的附件为准。线上引导页与授权链接已检查，真实账号经新插件核验及保存仍待本人验证。
> 用户已按 Chrome 指引真实确认 localhost:6000 可进入官方备用页；127.0.0.1:1 和 localhost:1 被拒绝。模拟验证及线上页面检查不替代真实订阅返回值确认。

## 1. 目标与范围

在现有 `commandcode-go-cliproxyapi` 插件中提供两种新增认证文件的方式：

| 入口 | 用户提供什么 | 最终凭据 |
| --- | --- | --- |
| CPA 的 OAuth 登录项 | 在官方网页授权，再复制官方生成的 key 回 CPA 完成 | CommandCode API key |
| 插件账户页的 API key 表单 | 手动粘贴已有 key | CommandCode API key |

只支持 **CommandCode GOAT / Pro / Max** 有效订阅，**不支持 CommandCode Go**。Go 使用官方 CLI 专用的私有接口与协议，并无本插件所用 Provider API 的访问权限；CPA 当前的 CommandCode 接入没有实现这套私有协议，换用 OAuth 也不能支持 Go。Provider、Team、Ultra 等不在本插件新增支持范围。插件名 `commandcode-go-cliproxyapi` 中的 `go` 继承自 `opencode-go-cliproxyapi`，不代表支持 Go 套餐。

这里的 OAuth 是“官方浏览器授权引导，复制凭据完成”，不是独立的 `access_token` / `refresh_token` 接入。不要宣称自动回调、自动续期或已取得标准第三方 OAuth 客户端资格。

OAuth 入口的易用性改进是：无需用户提前到官网手工创建 API key；官网在授权流程中生成凭据，用户从备用页复制回 CPA。两个入口可以并行共存，最终都是相同类型的认证文件，模型调用、核验和额度能力相同；仅来源标记不同，相同 key 仍去重，不同 key 不自动合并。更新摘要见 [ChangeLog](../CHANGELOG.md)。

初始设计约束（部署随后另行授权，不视为发布）：

- 只修改插件，不改 CPA 宿主代码、镜像或网络入口，不要求本机助手或端口转发。
- 兼容当前 CPA `v8.0.20`；若继续声明最低支持 `v7.2.138`，该版本也须通过新增流程验收。
- 两个入口新增前都联网核验身份与订阅；无法确认时不保存。
- 按 key 区分认证文件；同 key 不重复新增，不主动覆盖已存在记录的禁用状态、备注等字段。
- 同一官方账户的不同 key 可以各有一份认证，不按邮箱合并或自动替换。
- 认证文件仍是账户和密钥的唯一来源；旧配置 `api-keys` 不恢复使用。
- 不自动迁移、删除或批量重写旧认证文件。本轮准入检查只约束这两个新增入口，不宣称能约束宿主的所有文件上传入口。
- 本设计不包含部署、发布、标签或版本号调整。

## 2. 已核实的事实与尚未证实的条件

### 已核实

- 官方 CLI 的浏览器登录通过 `/studio/auth/cli` 授权，结果包含 `apiKey` 和账户信息。
- 当前官方网页既有表单 POST 回调，也有通过 `fetch` POST 回调的处理分支；不能把它直接等同于地址栏中含 `code` 的 OAuth 回调。
- 已查看的官方前端中，`fetch` 回调失败后会暂存生成的 key，并转到 `/studio/auth/cli/fallback`；备用页提供复制 key 的按钮。
- 官方备用页使用自己的 `sessionStorage`。CPA 插件不能、也不应直接读取其他网站的存储。
- GOAT / Pro / Max 具有 Provider API 访问权限；本轮继续使用现有 Provider API，不实现 Go 的 CLI 模型调用协议。
- CPA 插件的 `StartLogin` 可返回用户页面地址；`PollLogin` 成功后由宿主保存 `AuthData`。
- CPA 的插件资源页面可公开 GET；插件管理接口要求管理认证。两者可以分别承载静态引导和敏感提交。

### 已验证与尚待本人验收

1. 已验证官网接受 `http://localhost:6000/callback`，授权后用户能进入备用页；端口 1 被拒绝。
2. 已确认不带 `mode=redirect` 时使用 fetch 失败分支；不得改用表单跳转模式或虚构设备授权接口。
3. 已在真实 CPA 和 Chrome 中验证同源引导页、相对地址及新窗口；`/cpa/` 代理前缀通过模拟回归，不代表所有生产反向代理路径都已实测。
4. 引导页可以复用当前 CPA 登录状态调用管理接口；不得把管理密钥放入 URL。
5. 用真实订阅返回值确认准入所需的套餐标识、订阅有效状态及期限语义。

如果官方备用流程不再可用，停止 OAuth 部分并报告阻塞；不把普通手动添加成功冒充为 OAuth 已接入，也不自行扩大到修改宿主。

## 3. 用户操作流程

### 3.1 浏览器授权入口

```text
CPA → OAuth 登录 → CommandCode → 新增
                  ↓
        插件引导页：显示官方授权链接
                  ↓
      用户在本地浏览器打开链接并授权
                  ↓
       本机回调失败 → 官方备用完成页
                  ↓
     用户复制生成的 key，粘回 CPA 引导页
                  ↓
      插件核验身份、有效套餐、重复 key
                  ↓
        提示“已验证，等待 CPA 保存”
                  ↓
       CPA 轮询取得认证结果并保存文件
                  ↓
      CPA 确认完成，账户列表出现新认证
```

引导页必须说明：

- 这是“复制授权凭据完成”，不是复制回调 URL。
- 官方备用流程中的回调失败是预期步骤；不代表 CPA 已经取得认证。
- 官网不把认证 Token / API key 放进 Callback HTTP GET URL，而是 POST 返回凭据。授权通过后，可能短暂出现回调 URL 或认证传递错误提示，随后进入可复制凭据的备用页；这是故意触发备用流程的设计，不是要求用户重新授权。未跳转、不能复制或 CPA 核验/保存失败仍应按异常处理。
- 授权网站始终是官方站点；密码等登录信息不经过插件。
- 复制的 key 是秘密，可能经过剪贴板；粘贴完成后不要将它发到聊天或仓库。
- 官方显示授权成功，不等于 CPA 已保存；以 CPA 的最终状态和认证文件列表为准。

不尝试读取本机 `~/.commandcode/auth.json`，不安装本机 CLI 或助手，也不把 key 拼成所谓“回调 URL”。

### 3.2 手动 API key 入口

保留管理后台 → CommandCode → 账户与额度 → API key 表单。

改变现有“直接保存”的行为：先验证，再保存；页面显示“正在核验”，防止重复点击，并分别显示密钥无效、套餐不支持、网络失败、重复认证等原因。

两个入口使用密码输入框；成功提交后清空。插件不新增 key 的浏览器持久存储。官方页面自身的临时存储不受插件控制，不能宣传成“整个登录过程 key 从不进入浏览器存储”。

## 4. 故意触发回调失败的取舍

实施结论：采用 `http://localhost:6000/callback`，不带 `mode=redirect`。隔离 Chrome 测试确认端口 6000 被浏览器拦截，当前官方处理代码随后进入备用页；用户本人真实验证亦确认可进入备用页。端口 1 无论配 127.0.0.1 或 localhost 都被官网拒绝，不使用。

当前只对 Chrome 默认端口限制下的流程提供验证证据；其他浏览器未验证。不得通过启动参数解除端口 6000 的限制。插件不监听、不扫描、不转发该端口。

此前已接受的普通随机高位端口备选方案未采用，不保留自动降级到随机端口的逻辑。如果官网或浏览器行为变化，应停止并报告失败，不自动再授权或换端口。

## 5. 两个入口共用的内部处理

使用少量插件内部函数共用处理，不引入新的提供商、凭据仓库或通用认证框架。

```text
浏览器授权后粘贴 key ─┐
                     ├→ 规范化输入 → 身份与订阅核验 → key 查重/占用 → 构造同一种认证
手动粘贴已有 key ────┘
```

### 5.1 严格核验

- 只接受非空、无空白或换行注入的 key。
- 通过现有宿主 HTTP 调用能力查询 `/alpha/whoami` 和 `/alpha/billing/subscriptions`，沿用现有代理、TLS 和超时设置。
- 身份查询必须明确成功，不能仅凭 HTTP 200、浏览器自报的邮箱或旧缓存判定。
- 只接受已核实的 GOAT / Pro / Max 套餐原始标识与有效订阅状态；Pro 已知有不同版本标识，须逐项确认。
- 不把额度页的 `planFor` 前缀匹配和额度金额表当作准入规则。新套餐标识或状态未知时拒绝保存，并提示无法确认。
- Go、其他未支持套餐、无效或已过期订阅不保存。
- 网络错误、超时、上游限流或返回格式异常时不保存；交付宿主之前可以由用户主动重试。
- 验证不发送模型对话请求，不用付费推理“测试”密钥。身份与套餐核验通过，不代表还有额度或能使用所有模型。
- 账号请求的目标由受信任配置决定，不接受浏览器传入任意核验 URL。实施时用户已明确接受沿用 CPA 现有代理/TLS/HTTP 跳转规则：宿主没有插件可用的禁止跳转选项，部分跳转可能继续携带认证头；不再承诺严格阻止所有跨源转发。不为此改宿主或新建独立网络实现。
- 目录刷新另使用 `catalog-url`，并会向该地址发送启用账户的 `Authorization: Bearer <API key>`，即使目录本身公开可读。这个地址也必须是运营者明确可信的服务，推荐与 `base-url` 使用相同协议、主机和端口；当前配置校验不强制同源。不要把它指向陌生镜像或不可信地址。本轮仅补充文档警告，不改变现有请求或重定向规则。

现有额度查询对身份和套餐是尽力读取，不能直接复用整个 `fetchQuota` 作为严格核验；只复用适合的地址构造、请求能力和响应类型。

### 5.2 查重与占用

- 沿用完整 SHA-256 派生的文件名：`commandcode-key-<完整哈希>.json`。
- 检查宿主当前文件列表和 key，也识别用户自定义文件名，拒绝同名其他提供商文件。
- 两个入口共用按 key 哈希的进行中占用，覆盖核验后、等待交付以及已交付但保存尚未确认的阶段。
- 同 key 的第二个提交提示“已存在”或“正在保存”，不再次写入，不自动启用旧认证。
- 不同 key 不按邮箱合并；同一订阅的多个 key 不代表多份独立额度。
- 已交付但结果不确定时，不仅凭一个超时释放占用并自动重写。应先核对宿主当前记录；仍不能判断时停止并提示人工确认。
- 这些措施约束单实例中这两个插件入口；不是跨宿主上传入口、重启、多实例或文件系统操作的原子创建保证。

## 6. 认证文件与运行时兼容

两个入口都生成现有 `type: commandcode`、`api_key` 格式，可补充核实的邮箱、套餐标识以及新增来源。

来源字段实际使用 `credential_source: browser_authorization | api_key`，仅表示用户走过哪个新增入口，不作为凭据安全级别或官方授权证明。两种认证的使用能力没有区别。旧文件没有该字段时显示“已有认证”，不猜测来源。

关键约束：

- 文件名与运行时 ID 沿用现有规则，不另加一个会导致双身份的 JSON ID。
- 不伪造 `access_token`、`refresh_token` 或 OAuth 过期时间。
- 保持现有 `ParseAuth`、选中认证取 key、模型目录、执行器和额度管理的关系不变。
- 不自动刷新浏览器授权；key 被撤销或失效时提示重新授权或添加新 key。
- 手动粘贴任意有效 key 并不能证明它来自刚才那次授权，或与该次 `state` 有官方可验证的绑定；不作这类声明。
- 升级不改现有文件。新建时可写入已核实邮箱，但本轮不顺带修复或取消此前已接受的邮箱回写竞争限制。

## 7. CPA 接入分工

### StartLogin

- 创建高随机性、短期有效的登录会话，例如 32 随机字节及 10 分钟有效期。
- 返回插件同源的引导页地址，不把 CPA 传入的 `127.0.0.1` BaseURL 当作远程浏览器可访问的 CPA 地址。
- 页面可公开展示静态说明，但不能直接包含 key、管理密钥或任意账户详情。

### 完成提交

新增一个受管理认证保护的完成接口，概念路径为 `POST /plugins/<插件ID>/oauth/complete`。

- 接收会话标识与用户粘贴的 key；检查会话有效、未取消、未交付。管理页面需同源且启用“记住密码”，否则引导页禁用提交并提示重新登录。
- CPA 会对管理 JSON 的字符串做 HTML 转义；引导页用浏览器原生文本解析还原官方授权链接中的 `&amp;`，再校验官方地址、state 和本机回调。避免把转义后的 `amp;state` 当作正确参数；不改宿主。
- 进行共用核验与查重，占用该 key，将待交付认证仅暂存在进程内存。
- 返回“已验证，等待 CPA 保存”，不调用 `host.auth.save`，不提前报告成功。
- 管理密钥沿用现有页面的同源管理认证；不能通过 URL 传递，也不新增自己的管理密码存储。

### PollLogin

- 未完成时返回等待；过期或明确失败时返回清晰原因。
- 就绪后只交付一次 `AuthData`，由 CPA 原生 OAuth 保存流程落盘。
- 同一会话的并发轮询通过内部状态转换保护；已交付后的并发请求返回等待，不能返回错误污染宿主仍在保存的会话。
- 当前宿主会并发调用轮询，没有覆盖检查、交付、保存的统一锁，必须按实际调用方式测试。
- 浏览器引导页可调用 CPA 现有认证状态接口驱动轮询，即使原 OAuth 窗口关闭，也不需要另造保存流程。

### 手动 API key

- 现有 `/accounts` 接口通过共用严格核验、查重与占用后，继续调用 `host.auth.save`。
- 两种路径共用验证与记录构造，但 OAuth 不重复调用一次手动保存接口。

### 生命周期与取消

- 会话及待交付 key 不落盘；过期、插件停止或实际配置切换时清理未交付引用。宿主重发相同配置不清会话；交付后只保留摘要和确认状态至过期，避免旧版宿主保存触发重配置而丢失确认。
- 共享准入会先回收过期未交付会话；后台复用现有循环定期回收，空闲时也不无限保留。循环忙于目录刷新或生命周期操作时清理会延后；任何请求仍严格检查十分钟有效期。已交付或手动保存结果不明确的摘要不能因超时释放。取消与清理只能释放该会话尚持有的占用，重复清理不得删除后续提交的占用。
- 引导页取消应先标记插件会话取消，再取消 CPA 会话，阻止尚未交付的结果继续提交；如需新增插件取消接口，其用途仅为此。
- 宿主自身的取消没有插件通知，仍需依赖有效期清理未交付数据。
- 不能因页面关闭、插件回调返回或完成接口返回，就判断认证已经落盘。

## 8. 已接受的宿主保存限制

用户已确认保持只改插件，接受以下限制，并要求明确提示：

- **交付前可以取消；交付给 CPA 后不保证取消能撤回保存。** 宿主读取待处理状态后，可能先收到取消，再保存已经取得的认证。
- 插件没有宿主保存结果的确认回调。单会话最多交付一次，不等于全链路恰好成功保存一次。
- 保存失败或结果不确定时，不自动再次交付或再次写入；先刷新认证列表确认。
- 宿主现有保存能力不是原子的“仅当文件不存在时创建”。插件不会主动覆盖查到的旧认证，但不能保证与宿主同时上传、删除、禁用或编辑的操作绝不冲突。
- 页面在交付后显示“正在保存，请等待确认”，并建议不要同时操作同一认证；只有 CPA 最终确认及实际记录匹配后才显示成功。

如果未来要求“取消成功后绝不保存”、跨所有写入入口不覆盖，或严格的保存结果确认，需要宿主配套能力；不能通过多读一次文件或增加插件私有锁来宣称解决。

## 9. 开发与验收顺序

### 第一阶段：只验证可行性

- 不改线上部署，不读取现有认证 key，不自动替用户登录。
- 先用模拟凭据验证页面、秘密不进入插件 URL/日志/存储、受保护完成接口和状态转换。
- 再经用户明确授权，用本人浏览器进行一次真实官方授权，确认回调设置与备用页流程；这可能在官方账户中新建 key，不能当作无副作用查询。
- 验证同源引导页和 CPA 原生轮询能对接。
- 失败则记录具体阻塞，停止 OAuth 实施，不默默改成别的认证方式。

### 第二阶段：开发与针对性测试

- 实现共用身份/订阅核验与认证构造，更新原“保存不联网”的测试契约。
- 实现引导页、会话、完成提交及 CPA StartLogin/PollLogin 衔接。
- 为两个入口补充正确套餐、无效 key、Go/未支持套餐、失效/未知状态、网络失败及重复 key 测试。
- 测试同 key 跨入口并发、同会话并发轮询、提交后超时、明确保存失败及结果不确定的行为。
- 补充短期会话过期、重新配置/重启、重复提交和页面关闭测试，不把模拟测试作为宿主原子性的证明。

### 第三阶段：统一安全与回归验收
